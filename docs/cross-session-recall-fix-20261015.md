# 跨会话召回与自然表达 · 2026-10-15

本轮修复应用检索与回复衔接，沿用现有 Router、Executor、Memory 和 DeepSeek 生成服务，没有训练或替换权重。新版已加载到本地开发 Runtime，前端通过既有 API 使用。

## 实际问题

使用两个隔离的合成账号，在一个会话保存心情、宠物名字、放松偏好和试课经历，再从新会话询问。初始八项正向开发用例中，四项回答有目标事实依据；部分心情问法已经取得原话，生成却仍回答不知道，习惯问法则没有触发有效读取。该数字只描述这些开发用例，不是独立准确率。

另一个只读历史合成账号的检索显示：原话在数据库中，直接交给 4B 能判断相关，但没有进入 BM25 前八项、重排位次为 16，完整检索返回零证据。重复回顾问题挤占候选是原因之一。修复后目标来源进入 BM25 候选、重排第二，返回证据包含该来源。

还有两个衔接问题：4B 对含义接近的问法会给出相反判断；旧 prompt 又强制每次使用记忆都说“你之前提到”。调试中也发现，追问“你是怎么知道的”会丢失所问对象，导致上一轮有依据、下一轮反而否认。

## 修复方式

1. **保障事实读取。** 常见本人心情、已有偏好、宠物名字、历史事件的问法进入同一个 `memory_search`，不必要求用户说“请查记忆”。不将建议、未来预测、引文、第三人称或拒绝历史读取变成这类必需查询。来源追问只继承紧邻的用户事实问题，不从助手回答制造事实，也不跨越无关话题继承。
2. **在截断前排除空问题。** 纯回顾问题、询问空属性的名字/生日问题和单纯聊天控制语句不抢占答案候选；同条消息里真实陈述与提问并存时仍保留陈述。索引中的原文没有删除。BM25 仍最多查最近 2,000 条，近期候选扫描最多 96 条、保留最多 24 条，重排池最多 32 条。
3. **复用近期原话桥接。** 显式读取和可选背景读取都复用本人近期 SQL 原话补充索引，后台用途排除当前会话。SQL 与索引中的同一原话合并去重；所有权、来源角色、日期范围和模型每批最多 16 条的边界保持。
4. **轻量候选核对。** 4B 正常完成但没有接受任何证据时，仅显式本人事实查询可交付最多两条完整用户原话，放在独立的 `candidateEvidence`，由本来就要调用的生成模型核对主体、属性、否定、时间及关系。它们不计入 `evidenceCount`，不改模型分数或接受阈值，不增加一次生成调用，不用于自动背景召回。超预算的候选整条移除，避免截掉后半段更正或否定。
5. **自然融入回复。** 去掉背景、事实回顾和候选核对中的固定来源开场；有依据就先回答对应事实。旧情绪只能证明当时表达，当前纠正优先；时间变化、信息冲突或用户主动问来源时再说明依据。实际工具活动和来源仍可观察，不靠每句回答重复检索流程。

## 验证和限制

Python 全量 **530 项通过**，Ruff 通过；包含候选被重复提问挤占、混合陈述、所有权隔离、来源继承、候选结果序列化、完整原话预算及没有额外模型调用等检查。Java、前端和权重没有修改，未重跑此前的容量测试。

实服务验证通过前端代理、Java、Runtime 和已训练模型执行，使用专用合成账号，不在真实用户会话写消息。原始结果和阶段性失败均保存在本会话 `outputs/cross-session-fix-20261015/`，不发布私有凭据、业务数据库或真实用户聊天。

另外，账号 A 读取账号 B 会话被业务接口拒绝（HTTP 400，未返回记录）；回复中没有 B 的名字、地点测试标记。此检查只覆盖这两个账号。实际自然回复包括“芝麻团。”和“你平时喜欢在河畔书店听轻音乐，如果现在还有力气出门，去那里坐一会儿……”。在用户问“你是怎么知道的”后才说明同账号另一段对话中的原话。

这些是同一组合成事实上的开发复测，后续阶段积累了更多提问记录，未建立独立盲测集；保留全部失败阶段，不能将最终 22 项通过解释为任意真实对话的准确率。

这不是语义理解的完整解决方案。候选仍是有限窗口，未命中窗口、混合主体或复杂否定时可能遗漏；4B 仍可能误接纳问题，生成模型也可能拒答已有事实或偶尔保留来源开场。当前通过应用过滤和受限核对减少错误，不将开发用例成功率当作生产或临床保证。自动建议是否充分用到个人偏好仍有生成波动，不能仅因调用过记忆工具就判为个性化成功。
