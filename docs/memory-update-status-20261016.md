# 每轮记忆更新提示

新回复下方增加可展开的轻量提示，依据真实后台结果，区分聊天保存、近期索引和长期变更。

| 后台结果 | 显示 |
| --- | --- |
| 等待后台处理 | 正在整理记忆 |
| 普通账号原话索引完成 | 近期记忆已更新 |
| 实验账本实际变更 | 记忆已更新 |
| 无新增 / 拒绝长期保留 | 记忆已整理 / 未新增长期记忆 |
| 复核 / 部分变更 | 长期记忆待确认 / 部分记忆已更新 |
| 超时或故障 | 记忆更新待确认 |

`GET /agent/memory-updates/{requestId}`先校验当前JWT账号的业务receipt已保存，再查询内部Runtime。其他账号和未知请求均404，禁止缓存，不返回原文。前端最多查询10轮，超时可只读“重新检查”；切换会话或退出账号后停止更新旧提示，不重新执行写入。旧历史缺少requestId映射，因此不补造历史提示。

SQLite的`memory_updates`只保存每账号最近200条回执，不复制正文。新原话和初始回执同事务提交，修复两者短暂不同步造成的错误未知状态。长期变更完成后才记录成功，outbox重放不重置结果；回执可跨Runtime重启读取。45秒未完成转待确认，不把未知当成功。

经5175代理实测，长期变更约1,996ms、保留拒绝约901ms、普通近期索引约452ms后观察到结果。计时从memory-pending SSE开始，只是3个热开发样本，不是SLA。高频复核新事务方案观察到pending→indexed，没有出现回执竞态。

浏览器验证了“记忆已更新”和SSH中断时的“待确认”。当前业务库为本地H2，不是生产MySQL测试。专项Java测试27通过；前端状态/工具活动与语法检查通过；Python完整回归601通过，1条已有Starlette/httpx弃用警告。普通账号不启用实验长期写入，新0.6B门控仍是[离线候选](memory-fact-gate-06b-20261016.md)。
