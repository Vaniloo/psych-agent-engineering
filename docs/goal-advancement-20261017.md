# 聊天完成后的目标推进 · 2026-10-17

## 问题与改动

原先目标页的完成按钮会先保存check-in，再调用GoalCoachService判断目标完成或生成下一步。聊天链路只执行sync_goal_progress；规划服务还只接受manual来源。因此聊天里即使把唯一小步骤同步为done，也没有后续规划，下一轮只能读到“当前没有未完成步骤”。

现在聊天确认完成后依次执行：保存原始用户指令 → sync_goal_progress保存完成事实 → advance_goal核对完成标准或安排下一步 → 用实际回执回复。部分进展、休息、阻碍及未同步成功不自动触发这一步。新的advance_goal是完成阶段的受控写工具，不加入只读阶段的自由工具选择列表，也不需要重训路由模型。

新工具与目标页复用同一规划服务；输入包含目标标准、真实步骤/反馈、带时间的近期记录、相关近期用户表达，以及本轮尚未进入普通消息表的完整用户原话。每日/持续性目标不凭一次行动完成；可以为下一次合适时段安排一步。一次性目标须全部原步骤完成，模型判断达到完成标准且返回有效已完成步骤ID，才归为completed。

## 一致性与失败行为

- 后端根据实际check-in校验账号、目标、conversation来源、requestId、sessionId和本轮用户原话，调用者不能凭空指定一条未完成记录来规划。
- 对同一check-in加锁并缓存规划回执；重复请求不再调用模型或添加步骤。目标版本发生变化时拒绝把旧规划覆盖进去。
- 完成事实先单独提交。规划故障时仍保留done，并显示“下一步规划暂时不可用”；不把同步成功改报成失败。
- 规划成功后更新该记录对应的目标版本，并在私有coachingJson里保存规划前快照。撤销该次同步会一并撤销它自动生成的步骤/完成状态，恢复原步骤和反馈；后续手动调整或新进展导致版本变化时仍拒绝覆盖。私有快照不进入接口或模型提示词。
- 只有仍可操作的planned行动进入目标门控候选，保留它在目标内的原序号；已完成历史不占八个候选预算，避免每日追加步骤后很快因历史数量失效。

## 前端与回复

goal_progress先发送“已保存，规划中”，再用同一check-in更新为实际下一步或目标达成；重复、迟到的pending事件不能覆盖最终卡片，撤销后的卡片不被旧事件恢复。工具活动展示“判断目标完成与规划下一步”。

回复读取advance_goal回执与刷新后的目标，不再把规划前的快照当成最终状态；提示词里保留规划所需的小量结果，避免重复整个目标历史挤掉下一步。规划失败会明确说明已保存完成事实、下一步尚未生成，不询问用户是否要手动添加一条已经自动保存的步骤。

## 实服务验收

通过实际前端代理完成5轮SSE对话：持续目标聚焦、原截图表述“OK，今天的任务完成了”、追问“下一步呢”，以及一次性目标聚焦与完成。持续目标保存done后产生pending→ready事件，实际调用advance_goal并保存明天的一步；整体仍active，追问读取已保存步骤。一次性目标达到标准后归为completed，没有强行追加任务。重复推进未增加步骤，撤销恢复active和原planned步骤，错误原始请求被拒绝。原始合成结果见本会话outputs/goal-advancement-20261017/live-summary.json和live-turns.json，不随仓库发布。
