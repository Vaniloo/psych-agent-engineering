# 叙述式请求漏调动态工具（2026-10-19）

用户报告：直接问“86华氏度相当于多少摄氏度”会调用温度工具，但“有个弟弟吃饭问我，现在多少度，我说30摄氏度，他又问等于多少华氏度呢，怎么回答”仅用助手知识回答。

## 定位

真实4B评分重放中，工具已在获准候选里，当前原话完整送达。截图原句的工具分数为 -2.0625、TEXT 为 -0.625，选择 TEXT；另一条更长的数值换算请求则选择工具。还发现纯润色引文可能误选工具。分数为未经校准的 logits 差，不能解释成正确率或绝对效用。

主要问题是任务语义和应用的工具优先策略：模型可能将转述、如何回复理解为直接写文字。现有训练目标是公共数据中观察到的下一动作，不能保证优先取得每个可计算任务的实际工具证据。

## 当前修复

保留4B主选择和原始训练/服务渲染契约，增加有界语义复核：

1. 当4B准备停止、还有未执行的已授权动态读取工具、调用预算/时间仍充足时，每轮最多复核一次。
2. 复核使用现有生成模型，结合完整当前原话、有限历史、现有观察和动态工具描述/schema，判断 call / answer / clarify。
3. call 同时生成参数并提供当前原话中的依据片段；复用这次参数生成结果，避免再请求一次参数模型。
4. 选中的参数工具在原有参数生成阶段也可被放弃，避免把纯润色、概念解释或拒绝调用当作计算任务。完全由宿主绑定参数的原有快速路径维持原行为。
5. 校验权限、原话依据、schema、服务端绑定身份，再执行。不能增加工具、写入、账号或预算。失败不重试复核；初次停止保留，已选工具参数无法确认则澄清。

`dynamic_read_review.py` 不包含温度关键词或新工具名称匹配。新增普通工具仍通过注册表接入。`DYNAMIC_READ_STOP_REVIEW_ENABLED=false` 可关闭结束前的复核，已选工具的参数生成仍执行。

指标保留 `primaryAction`、`primaryProvider`、`dynamicReview`；改变初选时 provider 为 `semantic_review`。`pipeline.loop.dynamicStopReviewUsed` 和运行信息里的 `dynamicReadStopReview` 记录是否启用。该兜底效果单独报告，不计为4B训练效果提升。

## 实测

- 8条人工编写的开发检查：4条真实换算、纯润色、拒绝换算/解释概念、闲聊、缺数值；语义复核8/8符合预期，正例实际调用MCP得到86、30或77。复核及调用耗时约0.75–1.16秒。这些是开发样本，不是独立生产准确率。
- 隔离测试账号在**同一会话**经前端代理 → Java → Runtime → 实际模型/MCP，连续验证4条：短句与用户原叙述均调用；纯润色不调用；缺少数值不猜测、不调用。
- 用户原叙述的真实轨迹：知识/记忆读取 → 初选 finish → 语义复核选中温度工具 → 实际得到86°F → 回复。仅一次 `dynamic_read_action`，完整请求约5.97秒；原有内部检索也包含在此耗时中。
- 全量Runtime测试935 passed、1 skipped；随后补充澄清轨迹回归并复测相关测试。前端5组测试通过。

本会话证据位于 `outputs/narrative-tool-review-20261019/`：`baseline-scores.json`、`semantic-review-results.json`、`live-http-results.json`、测试日志。正式权重未变，只更新本地开发代码和服务。

## 尚存限制

复核会在“准备停止且仍有候选动态工具”的轮次增加一次生成模型请求；最多6秒，实测约1秒，计入用量。正常已选参数工具复用原有参数调用，不额外再加一轮。

此次未改变原路由的心理知识/记忆授权；温度问题仍可能先做多余的内部读取或补查，这部分已在轨迹中保留，需后续单独收敛。模型语义复核仍可能出错，动态注册贯通不代表任意工具、任意措辞都能准确识别。

后续同名多参数修复将停止复核更新为按观察进度限次，继续受读取预算/截止时间约束，详见[重复调用修复](dynamic-tool-repeat-fix-20261019.md)。本文一次复核的记录属于当时版本。
