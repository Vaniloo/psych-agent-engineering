# 并发与上线容量测试 · 2026-10-12

当前部署可做 **2～4 路活跃对话的受控试运行**，建议先按 **0.5 请求/秒**控制持续流量。短对话 4 路时表现较好；较长历史下，Router 4 路请求会超过当前 3 秒等待预算，应按 2 路更保守地配置。32 路虽然全部完成，但首字 P95 达到 19.5 秒，不能把“HTTP 成功”当作适合公开上线的并发能力。

这是一套真实开发部署的实测，不是生产集群容量证明：Java、Runtime、H2 文件数据库、Chroma、Ollama 与负载发生器运行在本机；模型经 SSH 转发访问 lab 的 GPU 0。lab 其他 GPU/CPU 上有共享工作负载，没有停止或调整其他进程。数据库、网络拓扑、TLS/反向代理与生产环境不一致。

## 范围与方法

- 32 个专用合成测试账号，每个账号独立目标、记忆和会话；不读写真实用户目标或对话。
- 完整链路包含前端 HTTP 代理、Java SSE、Qwen Router、Laya 工具选择、Qwen 目标判断、Qwen Memory/0.6B 重排、DeepSeek Flash、实际消息保存与 outbox。
- 场景覆盖普通聊天、知识检索、已有记忆查询、目标读取、部分行动进展与心理概要。分别增加较长回复、直接后端接口、同会话并发、幂等保存、停止接收和一次实际目标创建。
- 正常完整链路分档 1/4/8/16/32 路，闭环客户端依请求完成补发。另有固定到达 0.5 RPS 的 60 条测试，避免只用闭环结果掩盖排队。
- 模型服务单独测试，探测客户端最多等待 25 秒，并额外计算超出应用 2/3 秒预算的数量；“最终返回 200”不代表应用能在预算内使用该结果。
- 请求不自动重试。鉴权和账号余额可用性先验证，新 key 仅保存在私有配置，未进入仓库或报告。注册账号时遵守现有 10 次/分钟入口限制，没有关闭鉴权或限流。

临时工程诊断目标为首字 P95 ≤5 秒、总耗时 P95 ≤15 秒、生成与保存成功率 ≥99%，以及模型不可用降级 ≤1%。这是用于判断试运行的参考目标，不是用户已承诺的 SLA。

“成功”定义为回复生成并保存成功，不代表所有模型决策正确。204 条性能请求中有 33 条正常的低置信/未校准规则回退，与容量超时分开统计；49 条询问记忆的场景中，5 条没有进入记忆工具（4 条进入 chat，1 条 dashboard）。这是另外的工具路径覆盖问题，不冒充并发错误，也没有把它藏进 100% 成功率。25 条部分行动汇报均产生 1 次进度更新；本轮没有独立评分回复的心理支持质量。

Java 流式池当前 core=4、max=16、queue=200，实际线程快照观察到 4 个 agent-stream 线程。大队列在扩到 max 前承接请求。继续增加客户端并发主要增长等待；队列填满后再扩线程，还可能把压力转到串行模型服务。这是当前部署的重要上线限制。

## 实测发现并修复的故障

1. **Laya tokenizer 共享状态冲突。** 输入 token 预算检查在推理锁外编码，而推理线程使用同一 fast tokenizer。8 路探测出现 `RuntimeError: Already borrowed` 和协议/服务错误。已把编码检查移入同一锁；并发回归测试证明第二个请求只能得到正常结果或受控 busy，不能撞 tokenizer。仅重启本项目 Executor 服务，权重/校准没有改动。修复后突发超预算仍会 503，保留为容量限制。
2. **Qwen Memory 的工具返回类型过旧。** 独立 Memory 检索成功，但工具边界仅接受 rules/laya，拒绝 controller=qwen，并丢弃批处理/重排元数据。已补齐类型和字段，验证通过实际工具边界；正常测试有 44 次真实 Qwen Memory 调用，没有再次被类型拒绝。此前单服务评测未覆盖这条完整工具边界，本次把它补入回归。

没有为了压出更高分放宽模型接受阈值、修改风险规则、增加训练、删除困难场景，或直接扩大 Java 线程池。Python **321 项测试通过**，包含这两个修复的回归；Ruff 与差异检查通过。

## 并发正确性与恢复

- 同一账号、同一会话同时发送两条消息：两条回复对应自己的测试标记，保存 2 个完整轮次，消息增量恰为 4，没有丢失或混合。
- 相同请求 ID 同时提交两次保存：都返回 200，只增加 1 对消息，幂等正常。
- 分别在 meta、首 token 后关闭接收：客户端约 7 ms / 1.46 s 完成关闭；后续请求约 1.25 s 完成并保存，首字约 1.14 s。仅证明本次恢复，不能宣称停止接收会撤销服务器执行或计费。
- 实际调用目标创建：创建 1 个目标，约 3.63 s，前端活动事件为 running→ok。新 key 同时用于正常回复与后端目标生成。
- 跨测试账号读取另一账号会话：400 拒绝，没有返回记录；完整负载回放没有发现外来测试标记。

208 条正常完成的实际对话包括 204 条性能测试和 4 条完整性/恢复/创建对话；另有 2 条中断接收探测、2 次重复保存，以及分层与上游探测。204 条性能请求记录 Runtime 输入 171,239 / 输出 11,851 token；这不是全部账单，未包含单独上游探测、诊断、中断流、完整性请求和后端概要/目标生成。

结束后 Runtime 与所有活跃模型服务均就绪。后台任务第一页中没有待处理的测试账号记忆任务；这是分页观察，不冒充整个数据库 backlog 总量。

## 资源与测试排除

新资源采样覆盖附加测试、持续流量、完整性和长历史探测。GPU 0 最高利用率 100%，总占用显存峰值约 52.1 GiB / 95.6 GiB，包含多个常驻/历史服务，不是某个模型的单独显存。未观察到本次负载的 OOM；PyTorch 缓存会保留峰值分配，短测不能证明不存在长期泄漏。本机 Java/Runtime/代理峰值 CPU 约 17% / 15% / 2%，RSS 约 354 / 67 / 13 MiB，未显示本机 CPU 或内存耗尽。

原始数据完整保留，同时排除以下轮次的容量结论：

- 首轮对话与 Executor 故障复测有短暂重叠。
- 独立首轮在 Memory 类型修复前出现功能故障，不能称为并发容量不足。
- 一轮测试时 SSH 控制转发消失，模型连接被拒绝而应用仍生成规则回退回复。该轮是环境故障观察，不是正常容量数据。之后恢复转发、增加每档模型就绪检查，再重跑正常数据。

生产服务应通过稳定的内网服务地址访问 worker，并有依赖探活；不能把临时开发 SSH 转发当部署可用性保证。健康接口只检查 RAG 依赖时，仍可能出现“健康但模型已回退”，需要结合模型清单和实际降级记录。

## 上线前的优先顺序

1. **全局入场控制与短队列。** 初期限制 2～4 路实际处理，长历史按 2 路更稳妥；先以 0.5 RPS 灰度。队列设置等待期限，超出容量明确返回忙碌和重试提示。当前只有按用户/路径限速和 200 的线程池队列，没有适合交互体验的全局排队上限。
2. **Router 和目标服务的推理调度。** 优先验证跨请求合批、输入分档与有界等待；必要时在获准 GPU 上增加 Router 副本。单纯增大 Java 线程数会让模型排队更长，可能把等待变成风险/工具/目标判断降级。
3. **生产环境复测。** 使用正式数据库和网络拓扑，加入更长会话、峰谷流量与 30～60 分钟稳定性测试；分别统计模型降级、后台记忆积压、排队时间和端到端成功，不能只统计 200。

本轮没有发布生产版本、推送 Git、调动其他用户 GPU、删除真实数据或重启其他进程。测试账号与合成记录保留，后续可按专用前缀管理。
