# 同一动态工具多参数调用修复（2026-10-19）

修复前，一轮消息要求分别换算30℃和40℃时，只执行第一次工具调用，另一个数值由生成模型计算。模型看到工具在 `results` 中，就不再获得这个候选；结果也只按工具名保存最后一份。仅放开候选还不够，必须一起修复参数生成后的去重与观察记录。

## 最终行为

- 可以安全重复读取且有可变参数的动态 MCP 工具，在执行一次后仍可作为候选。内置记忆/目标读取仍沿用原来的查询恢复策略；无参数、全部参数由服务端绑定、不可安全重放的工具继续保持一次调用。目标写入走独立回执流程。
- 去重键为工具名与规范化后的实际发送参数。对象键顺序不影响身份，`30`与`30.0`视为同一数值，数组顺序和内容仍有区别。去重必须在模型完成新参数生成及 schema/身份校验后检查，不能提前拿上次参数判定。
- 执行前再次检查授权、只读属性、重复调用、次数和截止时间。若模型仍返回已有参数，结束本轮信息读取，不无限重试。
- 每次观察都保留参数、状态、结果。选择器、参数复核能看到调用历史；多次调用的最终回复上下文使用 `calls` 列表，避免后一次覆盖前一次；单次结果保留原结构兼容现有消费者。身份字段不进入动态调用观察摘要。
- 停止前语义复核由“每轮一次”改为“同一观察进度最多一次”。只有真正执行并观察了新调用，才可再次复核尚未覆盖的任务；复核本身不增加工具调用预算，调用次数和整体截止时间继续约束整个循环。运行信息公开该策略及上限。

新增 prompt 解释“一个结果只覆盖对应参数”，由模型判断下一个尚未覆盖的子任务和参数。这里没有新增温度/日期关键词规则，没有修改4B权重。工程逻辑负责候选、去重、权限和预算；4B与现有 DeepSeek 仍负责选择、语义复核和参数构造。

## 实际验证

使用真实模型及真实 MCP 单独记录参数/结果：

| 参数 | 工具实际结果 |
|---|---|
| 30 C → F | 86 F |
| 40 C → F | 104 F |
| -40 C → F | -40 F |

两组及三组输入均逐次执行。三组的独立读取循环中，前两次由4B初选，第三次由有界停止复核恢复；每次结果都保留在最终工具上下文。

通过真实前端 API、Java 后端及 Runtime 回放33组人工编写的开发案例，33组动态工具调用路径符合预期，共38次动态工具调用。包括原27组，以及新增两组日期、两组数组、三组温度、温度双向换算、同工具重复与其他工具混合、相同请求复用。只润色/翻译、缺参和原有长句用例均保留。最终源代码重新加载后又单独验证了一次原始双温度请求，确认部署版本实际调用两次。

这不是独立泛化评测。测试判断实际成功调用的工具及次数，回答关键词仅作冒烟检查；一条“零下 40”回复因旧标记缺少空格写法出现格式误报，回复数值及三次工具调用均正确，原始结果保留，案例标记补充等价写法。

33组完整请求耗时中位数6.73秒，范围4.28–14.12秒，包含生成回复及内部读取。新增多参数请求本来就需要更多工具和参数生成，因此不能把本轮混合样本当作性能提升结论。仍存在不相关的内置记忆/心理知识读取，未在本次修复中调整。
