# 面试讲解与代码阅读路线

先掌握一条请求怎样从输入走到保存，再理解模型训练。读代码时把“应用保证的行为”“模型预测”“检索证据”“生成表达”分开，很多追问都落在这四者的边界。

## 项目简介

**30 秒版本：**

我做的是一个带跨会话记忆、心理知识检索和目标推进的对话 Agent。Java 负责身份、安全和事务，Python LangGraph 负责有界工具循环。我把决策和生成拆开：Router 决定路线，Executor 在权限内选工具，Memory 筛选用户原话，最终回复由生成模型完成。项目重点是有限候选决策模型的训练与校准，以及通过证据校验、幂等写入、流式可观察性和过载控制，让模型错误不会直接变成越权或虚假的操作成功。

**三分钟版本：**

用户既会闲聊，也会问知识、回顾历史或推进目标。我没有让一个生成模型自由处理全部事情，而是先用本地决策角色判断路线、风险与支持需要，再由应用映射权限。Executor 在授权集合中读取工具，看到结果后继续、结束或澄清；读阶段有次数、期限和去重，空结果只允许一次查询修正。

记忆和公共知识分开。公共知识用 Chroma 与中文 BM25 混合检索；个人记忆保留原话、说话者、会话和时间，用 BM25、近期语义重排、相关性和充分性判断组织证据。最近修复了跨会话心情查询：不仅保障问法进入记忆工具，还补读已保存的近期消息，避免后台索引延迟和当前会话信息不足造成“我不知道”。

目标工具有写副作用，所以自由 loop 只开放读取。创建和进度同步走受控阶段，先保存原始命令，再校验目标判断、所有权、原话、版本和幂等，最终回复读取真实写入结果。消息与记忆 outbox 同事务提交，后台独立建索引。

模型也按任务做取舍：4B 在目标判断和 Memory 上有收益，工具选择收益较小但延迟更高，因此保留 Laya 处理工具选择、4B 处理目标。项目做过开发挑战、合成全流程和容量诊断，但没有独立临床评测；当前 loop 也还需要新一轮容量验证。

## 用一条请求讲透系统

假设用户在会话 A 说“今天我有点高兴”，随后在会话 B 问“我今天心情怎么样”。

1. Spring 从 JWT 得到同一个账号并验证会话 B 的归属，不相信前端传入的用户身份。
2. Router 预测路线，应用的 `personal_recall.py` 保障这类本人状态回顾开放并要求 `memory_search`。这是防止漏路由的应用策略，不把规则收益算成模型准确率。
3. 工具只查询本人原话：派生索引召回，加上近期实际消息补读；合并去重，排除他人陈述和纯提问，按“今天”的时区筛选。
4. 0.6B 重排和 4B Memory 判断相关性/充分性。模型只是证据筛选器，消息内容、账号和时间来自数据库。
5. 回答保留原话来源并说明“当时表达高兴”，不能把一条原话外推成全天一直高兴；后续有变化时最新表述优先。
6. 本轮消息与 outbox 同事务保存，后台更新索引。工具 trace 与保存状态能解释这一轮为什么这样回答。

排查同类故障按 **路由是否开放 → 工具是否实际执行 → 候选是否召回 → Memory 是否接受 → 证据是否进入预算 → 回复是否正确使用** 的顺序。盲目再训练只能覆盖其中一部分。

## 设计取舍与常见追问

### 为什么 Java + Python，而不是全用一个语言？

身份、用户归属、目标版本和事务已经在 Spring；模型、检索和图编排更适合现有 Python 生态。按职责拆分避免在 Python 重写业务权限。代价是服务鉴权、额外网络跳转和故障边界，因此内部 DTO 与契约测试很重要；这不是微服务越多越好。

### 与普通 LLM tool loop 有什么区别？

loop 结构是成熟的反馈循环，本身不是创新。项目的重点是把“路线授权”“动作选择”“记忆证据”变成独立有限候选决策，配合训练、校准与拒判；应用继续负责写权限和事实校验。生成模型只负责表达和受限规划。可以说是工程上的组合与取舍，不能说发明了新 Agent 算法。

### JEV、Laya、Qwen 到底是什么关系？

JEV/Laya 风格启发这里的结构化有限候选决策。Laya 用于训练和服务原有小决策模型；后来独立微调了 Qwen 4B，用固定候选渲染和 yes/no 分数构造概率判断。Qwen 的接入延续决策契约，不代表 Qwen 本身变成完整 JEV 模型。Memory 借鉴独立分类、相关性和充分性控制，没有完整实现 JEV-Mem 的语义/时间/因果/实体四视图图检索。

### 是三个模型还是四个？

三个决策角色。当前 Router 一个 4B worker，Executor 按工具/目标拆成 Laya 和 4B 两个 worker，Memory 一个 4B worker；另有原始 0.6B 重排与生成服务。角色、进程和基础模型数不是同一概念。

### 为什么不用一个大模型全做？

分开后可以限制工具候选、独立评测、校准与回滚，也能减少高频工具选择的大模型调用。代价是多份契约与部署，以及误差可能在路由、召回、筛选之间传递。项目实际对照表明工具判断的 4B 收益小于目标判断，因此按任务部署；不能声称所有请求都比通用模型更便宜。

### 训练如何防止数据泄漏？效果怎样说才可信？

按会话/场景 family 划分，检查重复和标签来源。训练集优化权重，校准集拟合温度，验证集选择接受阈值，候选用冻结挑战和旧版本回归检查。原始正确率、接受覆盖、错误接受和应用规则后的结果分别报告。许多标签来自程序场景或教师草稿，开发题也被用于诊断，因此不称为独立人工金标。详细数值引用对应日期的训练文档，不用当前小样本联调替代泛化评测。

### Memory 就是向量数据库吗？

不是。个人记忆当前主要是原话索引、BM25、近期语义重排和 Memory 判断；全历史向量召回尚未实现。公共知识 RAG 才使用 Chroma 向量与 BM25 融合。Memory 模型可以改善已召回证据的相关性与充分性判断，但没有召回的原话无法靠筛选模型找回来。

### 为什么 outbox？是否 exactly-once？

消息和待处理任务同事务，避免消息已存而记忆任务丢失；后台失败可以重试，索引按来源幂等写入。这是最终一致和幂等消费，不宣称全链路 exactly-once。已 DONE 的任务不会自动恢复丢失的完整历史索引，仍需备份/恢复流程。

### 为什么不用 LLM 自由写目标？

模型容易把未来计划、别人的行动或含糊指代当成用户已完成事实。应用先验证原始命令和候选，目标模型只能选择有限行动，Spring 再核对所有权、原话、版本与幂等。这样拒判会漏同步，但不会把模型猜测直接写成事实；用户仍能手动更新。

### 为何有 begin-turn 又有 persist-turn？

目标要在回复前落库，才能准确说是否创建成功；但不能先伪造一条完整回复。begin-turn 只记录原始命令凭据，persist-turn 最后保存真实消息并派发记忆任务。目标保存后回复失败仍可能出现不完整轮次，这个边界目前没有全自动恢复。

### LangGraph checkpoint 能恢复所有故障吗？

不能。它记录图状态，MySQL 才是业务事实源。当前 key 隔离用户、会话和请求，但没有实现自动续跑、同会话并发排序或跨工具事务。图用于显式节点、条件边和观测，不把框架能力等同于项目已实现能力。

### MCP 有必要吗？

默认同进程执行，省一次内部 HTTP。MCP 复用同一工具 Schema 和执行器，方便未来解耦工具服务；它是传输层，不是权限层。读失败可本地回退，已发送的写入结果不确定时不自动重放。当前共享 SQLite 适合单机，跨主机需要迁移。

### 上下文很长怎么办？

预算预留回复空间，按本轮证据优先组织工具、引用与近期历史，超限裁剪并显式标记。事实读取减少旧助手回答污染，不能把摘要空当成没检索到原话。当前估算器不等于真实模型 tokenizer 或计费 token，应承认这个误差。

### SSE 为什么比 WebSocket 合适？

当前以服务端单向 token/状态推送为主。fetch 的 POST 流能携带 JWT 与请求体，前端按 callId 显示真实工具状态。代价是断线/停止接收不等于后端取消，历史消息也未完整关联每次调用轨迹。

### 能承受多大并发？

当前普通流式入口默认 4 路执行、4 路短队列，超载快速拒绝，规则危机绕过普通队列。旧链路压测中 112 次尝试有 80 个接纳并保存、32 个拒绝；0.5 RPS 的稳定段 40/40。瓶颈主要是模型 worker 排队、工具和生成串行等待，不能把 4 个并发配置当作持续吞吐能力。新 loop 增加了复合读取和查询修正，尚需重新压测；没有水平扩展能力的实证。

## 面试前亲手做三个演示

用专用测试账号即可，不改真实用户数据：

- 新建会话说一个当天状态，切新会话询问，观察 `memory_search` 和有来源的回顾。
- 明确创建一个短目标，完成一步，再回顾已完成目标；确认卡片与数据库结果一致。
- 输入心理知识问题，打开引用和运行详情，区分知识查询、支持资源与个人记忆。

每个演示都能说明：模型做了什么、应用保证了什么、记录在哪里、出错如何定位。遇到尚未覆盖的情况直接说明边界，比背术语更稳。
